# Key Concepts Learned

## Requirements Analysis

Requirements Analysis is the process of reviewing and understanding software requirements before testing begins. It helps QA Engineers identify what needs to be tested and prevents misunderstandings later in the development cycle.

---

## Functional Requirements

Functional requirements describe **what the system should do**.

Examples include:
- User registration
- User login
- Add to cart
- Checkout
- Password reset

---

## Non-Functional Requirements

Non-functional requirements describe **how the system should perform**.

Examples include:
- Fast page loading
- Security
- Reliability
- Performance
- Scalability

---

## User Stories

A User Story describes a feature from the user's perspective.

Example format:

> As a user,  
> I want to reset my password,  
> So that I can regain access to my account if I forget it.

User Stories help the development team understand the value of a feature from the customer's point of view.

---

## Acceptance Criteria

Acceptance Criteria define the conditions that must be met before a User Story is considered complete.

For my Password Reset User Story, I created acceptance criteria such as:

- Password reset link should be sent to the registered email.
- User should be able to create a new password.
- User should be able to log in with the new password.
- Old password should no longer work.
- User should be able to request another password reset if necessary.

---

## Requirement Traceability Matrix (RTM)

The Requirement Traceability Matrix links requirements to test cases and test results.

It helps ensure:

- Every requirement has at least one test case.
- Missing requirements are identified.
- Test coverage can be tracked.
- Defects can be traced back to specific requirements.

# Biggest Lesson

I learned that successful testing starts long before executing test cases.

A QA Engineer must first understand the business requirements, identify what should be tested, and ensure every requirement is covered by one or more test cases.

---

# Challenges Faced

At first, I found it difficult to differentiate between User Stories and Acceptance Criteria.

After practising, I now understand that:

- A User Story describes **what the user wants to achieve**.
- Acceptance Criteria describe **how we know the feature works correctly**.
