## 🧠 What I Understood Better

One thing I am beginning to understand better is that SQL is not just about writing commands.

As a QA Engineer, I need to be able to look at a requirement or application behavior and think:

> "What should be stored in the database?"

Then I can use SQL to check whether the actual database state matches the expected result.

This makes SQL useful for investigating bugs and validating backend data.

## 🐛 Challenges and Mistakes

I am still getting used to SQL syntax and sometimes need to think carefully about the correct operator or structure to use.

Some mistakes are caused by remembering the general idea of a query but not the exact SQL syntax.

Instead of seeing these mistakes as failures, I am using them to identify areas that need more practice.

My main focus is to understand the logic behind each query so that I can eventually write SQL without relying heavily on examples.

---

## 🔍 QA Connection

SQL is becoming an important part of my QA toolkit.

For example, if a user performs an action in an application, I should be able to investigate whether the expected data was actually created or updated in the database.

A basic QA workflow could be:

1. Perform an action in the application.
2. Identify what database record should change.
3. Query the database.
4. Compare the expected result with the actual result.
5. Document any mismatch as a potential defect.
6. Provide the relevant evidence.

This is helping me understand how manual testing can extend beyond the visible UI.

* SQL can be used as a QA investigation tool.

* Writing SQL requires both syntax knowledge and logical thinking.

* Mistakes during practice are useful because they show exactly what I need to review.
* I should focus on understanding queries instead of memorizing them.
