# Day 63 — Learning Journal

## Topic
Test Case Management

## What I Learned

Today, I learned that effective QA involves more than writing test cases. Test cases must be organized, reviewed, updated, prioritized, and retired as the product changes.

I reinforced the difference between a test case, a test suite, a test run, and an execution result. I also learned why test case IDs and requirement traceability are important for maintaining coverage and communicating clearly with other testers.

## Important Lessons

- A test suite should be organized around related features or workflows.
- Duplicate test cases should be reviewed carefully before consolidation.
- Updated requirements may require revised test steps, expected results, or additional cases.
- Test execution should be prioritized according to risk, business impact, and failure likelihood.
- A test blocked by an unavailable dependency should be recorded accurately, with the reason documented.
- A historical pass does not prove that the latest build still works correctly.
- Clear test case titles make the suite easier to search, understand, and maintain.
- Obsolete test cases should be retired carefully without unnecessarily losing useful history.

## Practical Reflection

One important lesson was learning to distinguish a testing problem from a confirmed product defect. For example, if the payment service is unavailable, I should record the payment test as Blocked rather than incorrectly marking it Passed or Failed.

I also learned that test results must be interpreted in the context of the specific build and execution.

## Areas to Practice Further

- Link test cases to requirements.
- Maintain a record of test executions by build.
- Practice identifying duplicate and obsolete cases.
- Review test suite coverage after a requirement change.
