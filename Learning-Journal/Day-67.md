# Day 67 — Learning Journal

## Topic: Defect Metrics & Analysis

### What I Learned

Today, I learned how QA teams use defect metrics to monitor software quality, analyse testing results, and communicate risks before a product is released.

I learned that counting defects is not enough. A QA tester must understand what the numbers mean and how they affect the product.

The key concepts I covered were:

- Defect density
- Defect leakage
- Defect age
- Defect reopen rate
- Severity versus priority
- Root Cause Analysis
- Defect trend analysis
- Release risk assessment

### Practical Work

I worked through sample QA scenarios involving defect calculations and analysis.

I calculated:

- Defect density: 4 defects per KLOC.
- Defect leakage: 20%.
- Defect age: 5 days.
- Defect reopen rate: 10%.

I also interpreted defect trends across three builds and analysed a scenario involving multiple defects caused by a shared date-validation function.

Finally, I assessed an e-commerce application's release readiness using a defect report containing unresolved critical defects.

### Important Lesson

One important lesson from today is that a high number of resolved defects does not automatically mean an application is ready for release.

For example, an application may have 45 resolved defects but still contain 3 open critical defects.

As a QA tester, I must communicate those risks instead of recommending release based only on the number of resolved defects.

### Challenges

The main challenge was understanding how to interpret defect metrics rather than simply memorising their formulas.

I also reinforced the difference between severity and priority:

- Severity describes the impact of a defect.
- Priority describes how urgently it should be fixed.
