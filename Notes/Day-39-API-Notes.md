# Day 39 — API Chaining & Dependent Requests

## 📌 Overview

API chaining is the process of using data returned from one API request as input for another API request.

In real-world applications, API requests often depend on each other.

For example:

```text
Login
  ↓
Receive Token
  ↓
Use Token to Access Protected Endpoint
  ↓
Create Resource
  ↓
Receive Resource ID
  ↓
Retrieve / Update / Delete Resource
```

As a QA tester, API chaining helps you test complete workflows rather than testing each endpoint in isolation.

# 1. What Is API Chaining?

API chaining occurs when the output of one API request is used as the input for another request.

### Example

A user creates an account:

```http
POST /users
```

The API returns:

```json
{
  "id": 101,
  "name": "Pedro",
  "email": "pedro@example.com"
}
```

The returned `id` can then be used in another request:

```http
GET /users/101
```

Here:

```text
POST /users
      ↓
Extract id = 101
      ↓
GET /users/101
```

The second request depends on information produced by the first request.

---

# 2. Independent vs Dependent Requests

## Independent Requests

An independent request can run without information from another request.

Example:

```http
GET /users
```

The request does not require an ID generated by another request.

---

## Dependent Requests

A dependent request requires information from a previous request.

Example:

```http
POST /users
```

Response:

```json
{
  "id": 101
}
```

Then:

```http
GET /users/101
```

The GET request depends on the ID returned by the POST request.

---

# 3. Why API Chaining Matters to QA

Testing individual endpoints is not always enough.

An API may work correctly when tested individually but fail when used as part of a complete workflow.

For example:

```text
Create Account
      ↓
Login
      ↓
Get Profile
      ↓
Update Profile
      ↓
Logout
```

A QA tester should verify that the entire workflow works correctly.

API chaining allows us to test these relationships.

# 5. Postman Variables

Postman variables allow values from one request to be reused in another request.

Common variable scopes include:

* Global variables
* Collection variables
* Environment variables
* Local variables

For API testing, **environment and collection variables** are particularly useful.

Example:

```text
{{baseUrl}}
{{userId}}
{{token}}
```

Instead of writing:

```text
https://api.example.com/users/101
```

we can write:

```text
{{baseUrl}}/users/{{userId}}
```

---

# 6. Extracting Data From a Response

Suppose an API returns:

```json
{
  "id": 25,
  "name": "Pedro",
  "email": "pedro@example.com"
}
```

We may need to extract:

```text
id = 25
```

and save it as:

```text
userId = 25
```

The next request can then use:

```text
{{userId}}
```

Example:

```http
GET {{baseUrl}}/users/{{userId}}
```

---

# 7. Example API Chain

A basic workflow can look like this:

```text
POST Create User
       ↓
Extract user ID
       ↓
GET User
       ↓
PATCH User
       ↓
DELETE User
```

### Step 1 — Create User

```http
POST /users
```

Response:

```json
{
  "id": 25,
  "name": "Pedro"
}
```

Extract:

```text
userId = 25
```

---

### Step 2 — Retrieve User

```http
GET /users/{{userId}}
```

Expected:

```text
Status: 200 OK
```

The returned user's ID should match:

```text
25
```

---

### Step 3 — Update User

```http
PATCH /users/{{userId}}
```

Example body:

```json
{
  "name": "Pedro QA"
}
```

Expected:

```text
Status: 200 OK
```

---

### Step 4 — Delete User

```http
DELETE /users/{{userId}}
```

Expected:

```text
Successful deletion
```

---

### Step 5 — Verify

Attempt:

```http
GET /users/{{userId}}
```

Expected behavior depends on the API design, but a commonly expected response is:

```text
404 Not Found
```

This verifies that the resource was actually removed.

---

# 8. API Chaining Test Flow

A QA tester should think about the complete flow:

| Step | Request     | Dependency | Expected              |
| ---- | ----------- | ---------- | --------------------- |
| 1    | Create User | None       | User created          |
| 2    | Get User    | User ID    | Correct user returned |
| 3    | Update User | User ID    | User updated          |
| 4    | Delete User | User ID    | User deleted          |
| 5    | Get User    | User ID    | User no longer exists |

---

# 9. What Should QA Validate?

When testing a chained API workflow, validate more than status codes.

### Status Code

Example:

```text
200
201
204
404
```

### Response Body

Check that the returned data is correct.

### IDs

Confirm that the ID passed between requests is correct.

### Data Consistency

If a user was created with:

```json
{
  "name": "Pedro"
}
```

the subsequent GET request should return the expected user.

### Headers

Verify important headers such as:

```text
Authorization
Content-Type
Accept
```

### Authentication

Confirm that protected requests fail when the required token is missing or invalid.

### Response Time

Check whether the API responds within an acceptable time.

# 10. Positive Test Example

### Scenario

Create a user and retrieve the newly created user.

### Expected Flow

```text
Create User
     ↓
Receive ID
     ↓
Use ID in GET request
     ↓
Receive correct user
```

Expected result:

```text
PASS
```

---

# 11. Negative Test Example

Attempt to retrieve a user using an invalid ID.

```http
GET /users/999999
```

Possible expected response:

```text
404 Not Found
```

This tests how the API handles a resource that does not exist.

---

# 12. Another Negative Scenario

Use an invalid or missing authentication token.

```http
GET /profile
Authorization: Bearer invalid-token
```

Possible expected response:

```text
401 Unauthorized
```

This verifies that the API properly protects authenticated resources.

---

# 13. API Workflow vs Individual Endpoint Testing

### Individual Endpoint Testing

```text
Test POST
Test GET
Test PATCH
Test DELETE
```

Each endpoint is tested separately.

### Workflow Testing

```text
POST
 ↓
GET
 ↓
PATCH
 ↓
DELETE
 ↓
GET
```

The entire sequence is tested.

Workflow testing gives QA a better understanding of how the API behaves in a real application flow.

---

# 14. Common API Chaining Defects

During testing, look for issues such as:

* Incorrect ID returned after creation.
* ID cannot be reused in the next request.
* Created data cannot be retrieved.
* Updated data is not reflected in GET.
* Deleted data remains accessible.
* Authentication token is not accepted.
* Expired tokens are still accepted.
* Invalid tokens are accepted.
* Data from one user appears under another user.
* Required headers are lost between requests.
* API returns the wrong status code.
* API returns inconsistent response data.

---

# 15. QA Mindset

When testing API chains, ask:

### Before the workflow

* What data does the first request create?
* What values will I need from the response?

### Between requests

* Was the required value extracted correctly?
* Was it stored correctly?
* Is the next request using the correct variable?

### After each request

* Is the status code correct?
* Is the response body correct?
* Is the data consistent with the previous request?

### At the end

* Did the complete workflow achieve the expected result?
* Did the final state match the expected state?

---

# 🧠 Key Takeaways

1. **API chaining** means using the output of one request as input for another.
2. Dependent requests require data generated by previous requests.
3. Postman variables make it possible to reuse dynamic values.
4. IDs, tokens, and other response values are common chaining data.
5. QA should validate the entire workflow, not just individual endpoints.
6. Status codes alone are not enough; response data and relationships must also be validated.
7. Positive and negative scenarios should be included.
8. API chaining is useful for testing realistic application workflows.
